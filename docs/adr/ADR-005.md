## Context

Data quality today is implicit: eval gates (`eval_runs`), integrity checks
(`zolai_db_integrity_status`, FK guard), and ad-hoc validation scripts. The core checks we
most need are **Zolai-specific** — ZVS 2018 orthography, SOV order, ergative `in`,
unicode/text sanity, orphan references, POS tag validity — and these are custom Python by
nature. Meanwhile the generic-tools market shifted in 2026: **GX Cloud was discontinued**
(acquired by FICO; unavailable from 2026-06-01) while **Fivetran became steward of GX Core
in May 2026** (verified: greatexpectations.io/blog 2026-05-06, fivetran.com press
2026-05-13) — GX Core remains Apache 2.0 and viable later; **Soda Core relicensed to
Elastic License 2.0 at v4 (Jan 2026)** (verified: soda.io blog 2026-01-27 + GitHub LICENSE).

## Problem

Linguistic rules are unformalized: they live in validator modules and reviewer heads, not
in a registry that pipelines can run, record, and surface. We need (a) a single place to
declare quality rules with IDs, severities, and scopes; (b) run results persisted in the DB
(separate from model-quality metrics — a stated constraint); (c) Grafana surfacing of pass/
fail rates; (d) a gate hook for dataset publishing. Generic frameworks don't speak ZVS or
SOV anyway, so adopting them for the linguistic 80% would mean writing the same custom code
inside someone else's DSL.

## Options

1. **Build a pytest-style harness + DB rule registry** with Zolai rules as first-class
   entries; results into quality-run tables + monitoring (recommended).
2. Adopt Great Expectations (GX Core) and encode rules as Expectations.
3. Adopt Soda Core (ELv2) YAML checks.
4. Add dbt tests — inapplicable (no dbt DAG exists).
5. Keep ad-hoc scripts (status quo).

## Decision

**BUILD pytest-style harness + DB rule registry (incl. Zolai linguistic rules); DEFER GX/Soda.**
Tags: **BUILD** harness + registry + rule implementations; **CONFIGURE** results storage and
Grafana surfacing; **DEFER** GX Core to the >50-generic-rules trigger; **REJECT** Soda Core
(ELv2).

## Reasons

- **Linguistic rules are custom Python anyway** — a registry of Python callables behind a
  pytest-style runner is the shortest path; no YAML DSL translation layer.
- **Results belong in the DB** (`quality_runs` / `rule_results`, later surfaced like
  `eval_runs` already is via `/api/metrics/eval`) — consistent with DB-first observability.
- **Separates data quality from model quality** (constraint): quality runs measure dataset
  properties; `eval_runs` measures model/system behavior; both visible but distinct.
- **License safety:** Soda's ELv2 adds restrictions we don't need to accept; GX's Cloud
  product vanished and its stewardship changed hands — neither urgency justifies adopting
  a framework for the minority-generic rule set today.
- **Publish gate integration:** the dataset publish gate (batch 2 lifecycle doc) can call
  the harness directly — a function call, not a service integration.

## Consequences

- We own rule-engine plumbing: registry schema (`rule_id`, `scope`, `severity`,
  `implementation_ref`), runner, result tables, failure policy (warn vs block).
- Rule IDs become part of provenance: published datasets record which rules ran and passed
  (feeds the provenance chain: "which quality checks" — constraint question list).
- pytest compatibility means contributors can run `pytest` locally on rule suites —
  familiar DX, reuses dev dependencies already in `pyproject.toml`.
- Grafana gets a new quality dashboard panel (via existing metrics stack, ADR-002) —
  **extend, not new tooling**.
- Maintenance burden is ours — mitigated by keeping the registry thin (metadata + code refs).

## Rejected alternatives

- **Great Expectations now:** DEFER — solid Apache 2.0 fallback at >~50 generic
  non-linguistic rules; premature for ~10–20 generic checks while linguistic rules need
  custom code regardless.
- **Soda Core:** REJECT — ELv2 since v4 (verified) is a worse license than GX's Apache 2.0
  for no capability gain we need.
- **dbt tests:** REJECT — no dbt DAG; adding dbt purely for tests is a framework tail wag.
- **Status quo (ad-hoc validators):** rejected — gap G5 High; rules unformalized,
  unauditable, unreportable.

## Migration implications

- Phase 5 of the roadmap: harness + registry + initial rule set (generic: `TEXT_NOT_EMPTY`,
  `VALID_UNICODE`, `NO_ORPHAN_REFERENCE`; Zolai: `ZVS_2018`, `SOV`, `VALID_POS`, `ERGATIVE_IN`).
- Rule results tables are **additive DDL** (idempotent `CREATE TABLE IF NOT EXISTS`),
  consistent with existing eval-table creation — safe on live SQLite, later ported in the
  Postgres migration ([ADR-001](ADR-001.md)) untouched by renames ([ADR-015](ADR-015.md)).
- If GX trigger fires later: GX Core imports the registry's generic rules and runs them in
  suites; Zolai rules stay in the custom harness (hybrid, documented in a future ADR).
