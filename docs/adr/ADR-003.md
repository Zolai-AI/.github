# ADR-003: Defer Loki, OpenTelemetry, and Alertmanager; configure structured file logs

## Context

Operations today = one host running the FastAPI API (plus the monitoring compose stack).
Logs are currently plain files; there is no log aggregation, no distributed tracing, and
alerting already works through **Grafana alerting** with the three parity-gated rules.
Loki is AGPL-3.0-only (**verified** github.com/grafana/loki LICENSING.md, 2026-09-29);
Grafana core is AGPLv3 (verified). Tempo is also AGPLv3 (verified via the 2021
Grafana/Loki/Tempo relicensing post).

## Problem

Without a convention, logs stay ad-hoc (mixed formats, no rotation guarantees, grep-only
debugging). Conversely, standing up Loki + an OpenTelemetry pipeline + Alertmanager now
would add 2–3 services for a single-node, low-traffic system whose debugging needs are
already met by files plus the metrics/performance endpoints. Alertmanager would also
**duplicate** Grafana alerting — violating the no-duplication constraint.

## Options

1. **Configure structured JSON file logs + rotation now; defer Loki/OTel/Alertmanager**
   (recommended).
2. Adopt full ELK/EFK stack immediately.
3. Adopt Loki now (single binary) + OTel collector now.
4. Add Alertmanager alongside Grafana alerting.
5. Do nothing (no logging convention).

## Decision

**CONFIGURE structured JSON + rotation; DEFER Loki/OTel/Alertmanager.**
Tag: **CONFIGURE** a logging convention (JSON lines, rotation, severity field) on the
existing host; **DEFER** Loki, OpenTelemetry, and Alertmanager to their listed triggers.
Tracing as a whole is also **DEFER** (see Rejected alternatives; revisit: recurring
cross-service latency debugging — latency is already in `/api/metrics/performance`).

## Reasons

- **Single host/API** — file logs fully cover current debugging; `grep` + timestamps scale
  fine at this volume (constraint: evidence before infra).
- **Grafana alerting already handles alert parity** — Alertmanager would be a second,
  redundant routing layer.
- **OTel = a second pipeline** with no second service to instrument; premature.
- **Loki is AGPLv3** — fine internally (verified FAQ states internal log aggregation is
  unaffected), but it is still a new service against the zero-new-infra v1 rule.
- **Grafana-native future:** when/if Loki arrives, Grafana already talks to it — the
  deferral costs nothing in rework because the destination UI is unchanged.

## Consequences

- A repo-wide logging convention must be documented and followed by new code: one JSON
  object per line, stable keys (`ts`, `level`, `event`, `route`, `duration_ms`, …).
- Log search remains host-local; debugging across restarts depends on rotation settings
  (cap size/count).
- Alerts keep flowing only through Grafana → configured contact points (env-only secrets:
  `GRAFANA_ALERT_WEBHOOK_URL` etc., never committed).
- If log volume later becomes unsearchable, the escape hatch (Loki single-binary →
  Grafana) is cheap because dashboards/alerting already live in Grafana.
- Contributors must not add ad-hoc `print` debugging once JSON logging is configured.

## Rejected alternatives

- **ELK/EFK now:** rejected — multiple heavy services (Elasticsearch-class) for no measured need.
- **Loki now:** rejected for v1 — new service + AGPL distribution review before evidence of pain.
- **Alertmanager now:** rejected — duplicates Grafana alerting (no-duplication constraint).
- **OpenTelemetry now:** rejected — second pipeline with one service; defer.
- **Tracing (Tempo/Jaeger) now:** rejected — low-traffic single-node; latency covered by
  `/api/metrics/performance` (window-based p50/p90/p95/p99 by route).
- **Status quo with no convention:** rejected — gap G11 (Medium).

## Migration implications

- Phase 0/1: document the convention + wire rotation (logrotate/systemd journald caps) —
  small, reversible **CONFIGURE** work.
- Phase 10 of the migration roadmap explicitly **re-evaluates** Loki/GX/Dagster gates —
  the revisit triggers are tracked, not forgotten.
- When Loki is adopted (trigger met), ingestion starts from existing JSON files (no
  re-instrumentation), and Alertmanager remains unnecessary unless alert volume outgrows
  Grafana routing.
