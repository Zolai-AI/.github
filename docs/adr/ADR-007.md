# ADR-007: Dataset versioning via manifest + hashes + `dataset_versions` tables

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-29 |
| Decision owner | founder |
| Decision | **CONFIGURE manifest + hash + dataset_versions tables; DEFER DVC/lakeFS/Dolt** |
| Revisit when | Training artifacts >1GB leave Git → DVC for those |
| Evidence | [Tool matrix §3](../research/data-platform-tool-matrix.md) · [Current-state gap G6](../architecture/current-state.md) |

## Context

Published datasets must be **immutable with checksums** — a core project constraint — and
the provenance chain must answer "which dataset version did this sentence come from?"
Today, datasets are folders/exports under git-ignored `data/` plus prose manifests
(`data/DATA_INDEX.md`, `ARCHIVE_MANIFEST.json`); there is no enforced version ledger
(gap G6). The versioning market changed in 2025–2026: lakeFS **acquired DVC (Nov 2025)**
and lakeFS itself moved to **BSL 1.1 from v1.87.0 (2026-09-22)** while **DVC stays
Apache 2.0** (verified: lakefs.io/blog, 2026-09-29).

## Problem

We need (a) an immutable, checksummed record of every published dataset version; (b) a way
to trace any training/eval artifact back to exactly those bytes; (c) something that works
for files that never enter Git (constraint: large data never in Git) — without adopting a
service (lakeFS) or a niche versioned database (Dolt), and without committing large blobs
to Git (which is what naive versioning would tempt).

## Options

1. **Manifest + hashes + `dataset_versions` (+ file manifests) tables in the canonical DB**
   (recommended).
2. DVC for all dataset artifacts now.
3. lakeFS as the storage layer.
4. Dolt as the versioned DB for datasets.
5. Git tags/submodules for dataset files (violates no-large-data-in-Git).

## Decision

**CONFIGURE manifest + hash + `dataset_versions` tables; DEFER DVC/lakeFS/Dolt.**
Tags: **CONFIGURE/BUILD** `dataset_versions` schema + publish-time manifest writer
(rows: dataset id, version, created_at, content hash(es), row counts, source refs, quality
run id, publisher, immutability flag); **DEFER** DVC to the >1GB-artifact trigger;
**REJECT** lakeFS and Dolt.

## Reasons

- **Immutability is a DB-row property we can enforce cheaply:** version rows are
  insert-only; published blobs are written once and checksummed (SHA-256 per file +
  aggregate manifest hash).
- **Matches DB-first culture** — no new service; versions are queryable by every tool that
  already reads the canonical DB.
- **Git-agnostic:** manifests can describe files on local disk now, R2/B2 later
  (ADR-008) — storage location is a field, not an architecture.
- **License/status hygiene:** lakeFS's Sep 2026 BSL switch (verified) and Dolt's niche fit
  both argue against adoption; DVC remains the cleanest Apache 2.0 tool but only pays off
  for large files outside Git.

## Consequences

- Publish flow grows a mandatory step: compute hashes → write `dataset_versions` + manifest
  → run quality gate ([ADR-005](ADR-005.md)) → mark immutable (batch 2 lifecycle doc).
- Readers (training, eval, exports) must record the dataset version id they consumed —
  this closes two provenance questions ("which dataset version", "DVC/artifact version").
- We must guard immutability at write time (UPDATE/DELETE triggers or app-level checks);
  deprecation is recorded on a newer row, never by mutating a published one.
- Hash computation over multi-GB files costs I/O at publish time (acceptable; publish is
  rare).
- No diff/branch/merge UX like DVC/lakeFS — acceptable; we publish snapshots, not branches.

## Rejected alternatives

- **DVC for everything now:** DEFER — valuable only when training artifacts >1GB leave Git;
  until then manifests cover the need. (Note: DVC stays Apache 2.0 despite lakeFS
  stewardship — verified.)
- **lakeFS:** **REJECT** — BSL 1.1 since v1.87.0 (verified 2026-09-29): source-available,
  not OSI; running modified versions or offering services externally is restricted; also a
  new service.
- **Dolt:** **REJECT** — niche fit; doesn't map to "published dataset snapshots" workflow.
- **Git-hosted dataset files:** rejected — violates the large-data-never-in-Git constraint.

## Migration implications

- Phase 9 of the roadmap: provenance/immutability/versioning — add tables (**additive
  DDL**) and backfill versions for currently published datasets by hashing existing files
  (one-off script; backup before any rewrite per Phase 0 rules).
- Postgres move ([ADR-001](ADR-001.md)) is neutral: tables + hashes are portable; only the
  immutability triggers need dialect variants (SQLite vs PG) — plan both in Phase 2
  mapping ([ADR-015](ADR-015.md)).
- If DVC trigger fires: DVC tracks the large artifact files; `dataset_versions.dvc_version`
  (new column) links rows ↔ DVC revisions — additive change, no redesign.
