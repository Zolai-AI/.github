# ADR-008: Defer object storage

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-29 |
| Decision owner | founder |
| Decision | **DEFER** |
| Revisit when | Serving/publishing multi-GB artifacts → R2 (Cloudflare footprint) or B2 |
| Evidence | [Tool matrix §2](../research/data-platform-tool-matrix.md) · [Current-state §2](../architecture/current-state.md) |

## Context

All bulk data already lives on local disk in git-ignored `data/` (~2.3 GB canonical DB plus
corpus/backup folders). Nothing in the current product serves multi-GB downloads: the web
app, MCP server, and desktop app consume API responses, not raw blobs. Pricing for the
eventual move is known and cheap: **Cloudflare R2 = $0.015/GB-month, $0 egress** and
**Backblaze B2 = $6.95/TB-month** (both verified: official pricing pages, 2026-09-29).
Meanwhile the self-hosted S3 leader **MinIO was archived in February 2026** — repo marked
"NO LONGER MAINTAINED" 2026-02-12, community edition source-only, AGPLv3 (verified:
github.com/minio/minio, 2026-09-29).

## Problem

Object storage is infrastructure with ongoing cost (services to run, or per-GB billing) and
no current consumer. Adopting it "because data platforms usually have it" would violate the
evidence-first and zero-new-infra constraints. But deferring must be a *decision with a
trigger*, not an oversight — the provenance chain already has to anticipate where published
artifacts will live.

## Options

1. **Defer; keep local FS + git-ignored files** (recommended), with R2/B2 chosen at trigger.
2. Self-host MinIO.
3. Self-host Garage or SeaweedFS.
4. Adopt R2 now (pre-pay for unused storage/service).
5. Adopt B2 now.
6. Put large artifacts in Git (explicitly forbidden).

## Decision

**DEFER.**
Tags: **KEEP** local filesystem storage for now; **DEFER** cloud object storage to the
trigger; **REJECT** MinIO; **DEFER** (do not adopt now) Garage/SeaweedFS/R2/B2.
Revisit: serving or publishing multi-GB artifacts → **R2 preferred** (existing Cloudflare
footprint from MCP/landing) **or B2** for pure archival economics.

## Reasons

- **2.3 GB DB + local files suffice** for every current workflow; large data is already
  git-ignored, so Git is not carrying it (constraint satisfied).
- **MinIO is no longer a viable option** (archived Feb 2026, AGPLv3, source-only) — the
  historical default for self-hosted S3 is gone; adopting it now would inherit an
  unmaintained dependency (nixpkgs marked it insecure).
- **Garage/SeaweedFS = an extra service** to operate, patch, back up — cost without a
  consumer.
- **Cloud pricing is a non-decision at 2.3 GB:** ~$0.035/mo on R2 — meaning the eventual
  move is financially trivial and can wait for a real trigger; egress-free R2 is the right
  default when it happens (verified pricing).
- **Backups already have a story** (Phase 0 checksum baseline, cloud backup recommendation
  KR2.2) — object storage improves this later, not now.

## Consequences

- Publish/version manifests ([ADR-007](ADR-007.md)) must record a **storage location field**
  (path now; `s3://`/`r2://` later) so the eventual move is a backfill of pointers, not a
  redesign.
- Artifacts are only as durable as local disk + whatever manual/cloud backup is configured
  — the backup script (KR2.2) remains an important P0-adjacent dependency.
- No S3-compatible API exists for tools that expect one — currently none do.
- CDN-style distribution for published corpora is unavailable until trigger — acceptable;
  publications currently go through Git/HF/Kaggle-style channels (small files) anyway.

## Rejected alternatives

- **MinIO self-host:** **REJECT** — repository archived Feb 2026, AGPLv3, source-only
  distribution (verified); would be adopting dead infrastructure.
- **Garage / SeaweedFS:** DEFER — extra services; revisit only if self-hosted S3 becomes
  mandatory (e.g., an S3-only tool lands).
- **Adopt R2/B2 now:** rejected — no consumer; premature spend/complexity (however small).
- **Large files in Git:** rejected — violates the large-data-never-in-Git constraint.

## Migration implications

- Trigger work when it fires: create bucket → backfill publish artifacts (hash-verified
  against `dataset_versions` from ADR-007) → flip manifest location field → update backup
  job. Rollback = keep local copies (we never delete on cutover).
- DVC's storage interaction (if ADR-007's trigger also fires) can point remote cache at
  R2/B2 — both are S3-compatible.
- No impact on the SQLite→Postgres path ([ADR-001](ADR-001.md)); object storage is for
  blobs, not rows.
