## Problem

The same AI-surface concerns are being solved five times: tool shapes, MCP transport details,
tier gating, chat UI behavior, and utility/token helpers. Duplication has no single owner, so a
tier-map change in `zolai-core` can silently desynchronize all clients; meanwhile `cn()` exists
in three hand-written copies plus a fourth package-based variant. A shared package would give one
contract surface, but the root has no workspace to host it, and every consumer ships through a
separate CI/deploy pipeline. Any packaging choice must therefore respect repo independence and
must not put provider keys or token material into a browser/desktop bundle.

## Goals / non-goals

- **Goals:** one typed contract for tools + MCP client; one token palette/motion contract; one
  chat behavior implementation; injectable credentials; generated types with CI drift failure.
- **Non-goals:** redesigning consumption pipelines; merging nested repos; making `zolai-web`
  adopt the Vercel AI SDK; shipping styled shadcn primitives; implementing any code in this ADR.

## Options

1. **Standalone package repo, published to GitHub Packages; `bun link` for local dev** —
   *chosen*. Preserves all five independent repos and deploy pipelines; gives one versioned
   artifact with an explicit consumer opt-in. Trade-off: each consumer CI needs GitHub Packages
   auth (`GITHUB_TOKEN` with `packages:read`), every release needs a version bump and pinned
   upgrade across four repos, and `bun link` must be documented so linked builds do not leak into
   deployed lockfiles.
2. **Root Bun workspace restructure** — rejected: no root `package.json` or workspace exists
   today; introducing one changes install/build behavior for independent repos and couples their
   deploy pipelines. Disproportionate to a shared contract layer.
3. **`file:` sibling dependency** — rejected: sibling paths are not stable in independent CI
   checkouts, produce path-dependent lockfiles, and blur package-version boundaries; useful only
   as a temporary local experiment, not a supported contract.
4. **Copyable templates / duplicated utilities** — rejected as the *strategy* (it is the current
   failure mode); retained only as the rollback path per phase below.

Standalone wins because it is the only option that creates a versioned, reviewable boundary
without changing repo topology. Its costs (CI auth, version pinning) are explicit, bounded, and
reversible; the workspace option's costs are architectural.

## Decision

**PROPOSE (not approve)** a new independent repo (working name `zolai-ai-kit`) publishing
`@zolai/ai-kit` to GitHub Packages. Consumer repos remain independent.

### Package layout and exports (proposed)

```
zolai-ai-kit/
  package.json          # name @zolai/ai-kit, ESM, exports map, optional peerDeps
  src/types/            # ToolDefinition, Tier, MCP request/response contracts, generated API types
  src/client/           # MCP HTTP client: endpoint config, JSON-RPC envelope, OAuth token getter
  src/tools/            # framework-neutral registry + framework adapters
  src/react/            # headless chat behavior (hooks/components), no styled primitives
  src/tokens/           # primitive→semantic→component token data, CSS variable emitter
  scripts/              # regenerate types from zolai-core contract; drift check
  tests/                # contract tests, adapter snapshots, tier-count assertions
```

Exports map (five subpaths; root export may re-export only `types` + `client`):
`@zolai/ai-kit/types`, `@zolai/ai-kit/client`, `@zolai/ai-kit/tools`,
`@zolai/ai-kit/react`, `@zolai/ai-kit/tokens`. No deep imports beyond this surface.

### Per-consumer import matrix (proposed intent)

|---|:---:|:---:|:---:|:---:|:---:|---|
| `zolai-web` (Next 16, SSR/server routes) | ✅ | ✅ | ✅ | ✅ | ✅ | Keeps its existing provider SDKs; adapters bridge them. Provider calls stay server-side. |

| `zolai-tauri/frontend` (`zolai-studio`) | ✅ | ✅ | ✅ | — | ✅ | Phase 4 offline adapter; no cloud token embedded in the desktop bundle. |

### Tool definitions, handlers, tiers

- A tool definition is **framework-neutral data**: stable `id`, `name`, `description`,
  `tier: 'public' | 'member' | 'admin'`, JSON Schema for input/output, and capability metadata.
  It contains **no executable handler and no credentials**.
- Adapters: `toVercelTool`, `toOpenAITool`, `toAnthropicTool`, `toMcpTool` convert the same
  definition into each framework's expected shape. Adding an adapter does not change the source
  definition. `ai` (Vercel AI SDK) is a **new** dependency for consumers that opt in — none has it
  today, so no consumer is required to adopt it.
- Server-side handlers are **injected** by each consuming app through an explicit handler map;
  the registry never imports provider code or executes calls. Tier enforcement remains in
  `zolai-core` (8 public / 31 member / 39 admin); the client mirrors tier metadata for UI gating
  only and treats the server as authoritative.
- Token acquisition is an injected `getToken(): Promise<string | undefined>` supplied by the
  caller. The kit never reads environment variables, never reads key files, and never embeds
  keys, OAuth client secrets, or bearer tokens. [Architecture invariants](../../context/architecture.md)
  and [root AGENTS.md](../../AGENTS.md) §Secret Hygiene apply to every bundle and CI log.

### Dependencies and UI scope

- `react`, `ai`, and `zod` are **optional peer dependencies**, each behind its own subpath;
  importing `types`/`tokens` must not pull any of them into a bundle.
- Share **behavior and tokens**, not styled shadcn primitives. `react` exports headless chat
  state/message contracts; each app supplies its own visual primitives and styling.
- `cn()` duplication is **not** removed by this decision; it is a candidate for removal only
  after the ordered improvement steps below.

## Ordered improvement decisions

These five steps are an ordered procedure, not parallel workstreams. Later steps may not begin
before earlier ones are evidenced.

1. **Question requirements.** Name an accountable owner for the package and for each consumer
   migration; cite the evidence path for every requirement. No owner is named in current
   evidence, so the owner is **needs-founder**, not an invented role or a presumed approval.
   Unverifiable claims are marked UNKNOWN and opened in `docs/strategy/decisions.md` per the
   [source-of-truth conflict rule](../governance/source-of-truth.md). This ADR is PROPOSED until
   that assignment and sign-off occur.
2. **Delete unnecessary parts.** Before removing any duplicated `cn()` helper or fetch wrapper,
   produce a caller/dependency analysis, characterization tests for current behavior, and a
   documented rollback. Only then delete; verify with the existing build/test commands. A
   "10% add-back" allowance is a heuristic for judging over-deletion, **not** a deletion quota
   or permission to leave untested gaps.
3. **Simplify / optimize only what remains.** Against the measured baseline (bundle size,
   type-check time, request count), simplify the retained surface; no new abstraction is added
   unless it reduces a measured cost. Re-run the same baseline command after each change.
4. **Accelerate cycles only after 1–3.** Faster release cadence or broader rollout may start
   only when ownership, deletion safety, and simplification are evidenced. No gate is skipped:
   typecheck, tests, lint, GitHub Packages auth check, and secret-hygiene diff scan still run.
5. **Automate last.** Automation (type regeneration, CI contract check, publish) requires a
   proven reversible manual process first: bounded authority (least-privilege `packages:read`
   in consumers, scoped publish identity in the kit repo), an audit trail (commit SHA + package
   version in artifacts), and a tested rollback (pin the previous version). No auto-publish on
   an unproven pipeline.

## Phased rollout

Each phase is independently revertible; none starts before the previous phase's verification is
recorded and the ordered improvement steps are respected.

| Phase | Scope | Verification command | Rollback |
|---|---|---|---|
| 1 | Publish `types` + `client`; migrate **zolai-explorer first** | `cd zolai-ai-kit && bun run typecheck && bun test` then `cd zolai-explorer && bun install && bun run typecheck && bun run build && bun test` | Revert explorer lockfile/imports to the prior commit; unlink local package; keep the published version (do not unpublish) |
| 2 | Tool registry + four adapters; generated tier map from `zolai-core` | `cd zolai-ai-kit && bun test` with contract snapshots asserting **8 / 31 / 39** tiers and adapter shape equality | Pin previous kit version in consumers; restore local handler maps from the pre-adapter commit |
| 3 | Headless React chat in **zolai-web + zolai-explorer** | `cd zolai-web && bun run lint && bun run test:unit && bun run build`; `cd zolai-explorer && bun run build && bun run verify:browser` | Revert chat routes/components to prior commit; pin previous kit version; confirm no provider key entered any client bundle |
| 4 | Tauri offline adapter for `zolai-studio` | `cd zolai-tauri/frontend && bun run lint && bun run build`; manual offline smoke with network disabled (no token, no cloud call) | Revert frontend imports/lockfile; retain the previous offline behavior; re-run build to confirm |
| 5 | CI contract check: regenerate types from `zolai-core`, fail on drift, reconcile `docs/mcp-surface.md` status | `cd zolai-ai-kit && bun run scripts/check-contract.ts` (exit 1 on drift) plus all four consumer `build`/`typecheck` commands | Disable the failing check by pinning the last matching generated commit; open a drift issue, never bypass by hand-editing generated files |

## Risks / open questions

- **CI auth to GitHub Packages** is unverified in each of the four consumer repos; `packages:read`
  and publish identities need an accountable owner (needs-founder) before Phase 1.
- **Version pinning across 4 repos** via [ADR-007](ADR-007.md)-style manifests/hashes analogy:
  who bumps versions, what is the support window, and how drift is waived with audit.
- **No Vercel AI SDK dependency today** — `ai` is an optional peer only; adopting it is a
  separate consumer decision, not an implicit effect of this ADR.
- **landing/journey** probably should consume only `tokens`/`types`; confirm before any chat or
  client import reaches a cinematic bundle.
- **zolai-tauri offline behavior** — offline tool execution and token-free operation need a
  defined contract; desktop bundles must never carry a provider key.
- **Secret hygiene** — every phase must pass the root secret-hygiene rules; no real secret may
  appear in tracked files, docs, logs, or test fixtures. Scan staged diffs before any commit.
- **Doc conflict** — `docs/mcp-surface.md` currently labels the MCP surface PLANNED/not
  deployed while root AGENTS.md records it live. This ADR cites the live URL as verified context
  and treats that doc as stale evidence to be reconciled in Phase 5, not as authority for liveness.
- **No implementation approval** — PROPOSED + needs-founder means this document grants no
  permission to create the repo, publish a package, change consumer manifests, or run rollout.

## Rejected alternatives

- **Root Bun workspace restructure** — no workspace exists; would couple independent deploy
  pipelines and change install behavior for all consumers.
- **`file:` sibling dependency** — unstable in independent CI, path-dependent lockfiles, weak
  version boundary.
- **Copyable templates as strategy** — perpetuates the `cn()`/fetch-wrapper duplication this
  package exists to end; retained only as rollback.
- **Styled shadcn component package** — couples five visual systems to one theme; share tokens
  and behavior instead.
- **Bundling API keys or an ambient token getter into the kit** — violates root secret hygiene
  and architecture invariants; tokens are injected by callers, server-side only.
