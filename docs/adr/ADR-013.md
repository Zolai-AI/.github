# ADR-013: Defer MLflow experiment tracking

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-29 |
| Decision owner | founder |
| Decision | **DEFER MLflow** |
| Revisit when | zolai-training runs >10/mo needing comparison → MLflow |
| Evidence | [Tool matrix §12](../research/data-platform-tool-matrix.md) |

## Context

Experiment history today comes from two DB-first sources: **`eval_runs`** (full metric
history for every eval invocation, surfaced via `/api/metrics/eval`) and **`pipeline_runs`**
([ADR-006](ADR-006.md), planned) for batch jobs. Training in `zolai-training` is
RAG/LoRA-light: infrequent runs producing GGUF artifacts, not a hyperparameter-search
program. MLflow was verified 2026-09-29: **Apache 2.0** (GitHub LICENSE.txt), active 3.x
line (3.15.x), deployable as a single container with **SQLite default backend** — i.e. it
is genuinely cheap *if* needed. "Single-container SQLite" convenience claim:
unverified — secondary source (plan), license/release verified.

## Problem

Without tracking, comparing two training runs means reading scattered logs/notes; with
tracking added too early, we'd run a service and discipline (runs, artifacts, params) for
~a few runs a month where plain records suffice. We need a defensible line between "our DB
already covers this" and "we need an experiment server".

## Options

1. **Defer MLflow; keep `eval_runs` + run notes/manifests as history** (recommended).
2. Adopt MLflow now (single container, SQLite backend).
3. Adopt a SaaS tracker (W&B/Comet cloud) — data egress, cost.
4. Hand-rolled experiments table (no tool).

## Decision

**DEFER MLflow.**
Tags: **CONFIGURE** lightweight run records in our DB/manifests for now (run id, git
commit, dataset version, config, metrics — linking to [ADR-007](ADR-007.md) version ids);
**DEFER** MLflow to the >10-runs/month-comparison trigger; SaaS trackers rejected.

## Reasons

- **`eval_runs` covers metric history already** — the thing experiment tracking mostly
  provides for us is already in our own DB with Grafana surfacing.
- **Training is light (RAG/LoRA-light)** — run counts are low; comparison overhead is low.
- **Constraints:** zero-new-infra v1 + no data leaving the host (SaaS rejected on that basis).
- **Cheap re-entry:** because MLflow is Apache 2.0 + single-container SQLite (verified
  license; backend claim unverified — secondary source), deferring costs nothing — adoption
  later is an afternoon, not a migration.

## Consequences

- Run comparison UX is manual for now (side-by-side reading of run records/manifests).
- Discipline requirement: training runs must actually record config + dataset version +
  metrics in a consistent format, or history is worthless — this convention is part of the
  pipelines docs (batch 3).
- Artifact bytes (checkpoints, GGUF) stay git-ignored local files; version references point
  at `dataset_versions`/manifest hashes ([ADR-007](ADR-007.md)) rather than an artifact store.
- When trigger fires, MLflow imports historical runs from our records (one-off backfill
  script) so history isn't stranded.

## Rejected alternatives

- **MLflow now:** rejected — no measured need; a service and a tracking discipline for a
  handful of runs/month fails the evidence-first bar (despite being cheap to run).
- **SaaS experiment tracking:** rejected — corpus/model metadata leaving the host + cost +
  vendor lock-in; conflicts with self-host-first posture.
- **Ad-hoc notes with no structure:** rejected — replaced by the run-record convention
  above (better than prose, cheaper than MLflow).

## Migration implications

- Trigger work when >10 runs/mo need comparison: deploy MLflow (container, SQLite or point
  at Postgres after [ADR-001](ADR-001.md) cutover), register past runs via backfill,
  point `zolai-training` at `mlflow.log_*` calls — additive integration, no data rewrite.
- Run records/manifests produced now remain readable after adoption (backfill input).
- DVC interaction (if ADR-007 trigger fires) composes: MLflow tracks runs; DVC tracks
  large files; our `dataset_versions` remains the dataset authority.
