# ADR-016: Analytics (BI) ownership — operational vs data vs AI/RAG dashboards

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-30 |
| Decision owner | founder |
| Decision | **CONFIGURE dashboard ownership split: operational = Grafana only; data + AI/RAG = Zolai Admin (Grafana `data` folder interim); DEFER Superset/Metabase** |
| Revisit when | First community analyst self-serve need (need = UNKNOWN, **needs-founder**) → Metabase (light) first; Superset only if governance-heavy BI is required |
| Evidence | [Observability §0/§6](../architecture/observability.md) · [Tool matrix §7](../research/data-platform-tool-matrix.md) · [Current-state gap G12](../architecture/current-state.md) |

## Context

The project separates **operational observability** from **analytical dashboards** by standing
constraint (no duplication across Grafana/Superset/OpenMetadata/Admin). Operational dashboards
already exist: Prometheus 3.15 + Grafana 13.2.3, 3 provisioned dashboards, unified alerting
([ADR-002](ADR-002.md)). Two other dashboard classes are named in the brief but unowned today:
**data dashboards** (records, datasets, POS distribution, quality failures, annotation progress)
and **AI/RAG dashboards** (eval pass/fail, retrieval quality, latency — surfaced DB-first from
`eval_runs` / planned `rag_traces`, [ADR-012](ADR-012.md)). The thin Next.js admin
([ADR-009](ADR-009.md)) is the planned home for domain UX. BI candidates were verified in the
tool matrix §7: **Superset 6.0** Apache 2.0 but a 4-part stack (web, worker, Redis, metadata
DB); **Metabase** AGPL single container with Pro (from $575/mo) gating SSO/RLS.

## Problem

If no owner is declared, data/AI dashboard requests either land in Grafana (blending
operational and analytical views — the exact duplication the constraint forbids), get built
twice when a BI tool eventually arrives, or stall as ad-hoc SQL. We need an explicit owner per
dashboard class and a cheap interim, without standing up a BI stack for a consumer set that
does not yet exist.

## Options

1. **Ownership split with interim Grafana `data` folder + Zolai Admin analytics section; DEFER
   standalone BI** (recommended).
2. Superset now as the data-dashboard home.
3. Metabase now as the data-dashboard home.
4. No dashboards for data — SQL only, on demand.

## Decision

**CONFIGURE the three-way ownership split; DEFER Superset/Metabase.** Tags: **CONFIGURE/KEEP**.

| Dashboard class | Owner (v1) | Backing store | Revisit |
|---|---|---|---|
| **Operational** (API traffic, DB health, pipeline runs, alert state) | **Grafana** (sole owner) | Prometheus `/metrics` + `/api/metrics/*` | never, unless Grafana licensing posture changes ([ADR-002](ADR-002.md)) |
| **Data** (records, datasets, POS distribution, quality failures, annotation progress) | **Zolai Admin analytics section** ([ADR-009](ADR-009.md)); **interim before Phase 8 = Grafana `data` folder** (sole owner during the interim — it moves, it never doubles) | canonical DB tables (SQL) | first community analyst self-serve need → Metabase (light) or Superset (governance) |
| **AI/RAG** (eval pass/fail, gate history, retrieval quality) | **Zolai Admin + eval tables** (DB-first, [ADR-012](ADR-012.md)); Prometheus/Grafana keep **latency metrics only** | `eval_sets`/`eval_cases`/`eval_runs` (+ planned `rag_traces`), `/api/metrics/eval` | RAG regressions untraceable from evals → Phoenix first ([ADR-012](ADR-012.md)) |

**Hard rule: never the same dashboard in two tools.** A panel exists in exactly one owner;
the other surfaces may link to it, not clone it.

## Reasons

- **The consumer set for BI is empty** (stated in [observability §6](../architecture/observability.md)):
  nobody yet needs self-serve explore; the founder reads SQL and Grafana.
- **Marginal cost of the interim is zero** — Grafana already runs, and the admin analytics
  section ships with Phase 8 work that is happening anyway ([ADR-009](ADR-009.md)).
- **Superset is a 4-part stack** (web, worker, Redis, metadata DB) — violates the zero-new-
  services posture for v1; **Metabase is single-container but AGPL** with paid gates on the
  SSO/RLS features we would eventually want.
- **Ownership, not tooling, is the decision that ages well:** when the trigger fires, the new
  BI tool inherits the *data* class only; Grafana keeps operational, admin keeps AI/RAG.
- Aligns with the invariant "separate operational obs from analytical dashboards"
  ([overview §5](../architecture/overview.md#5-invariants-standing-rules--violations-block-merge)).

## Consequences

- Data-dashboard requests are answered in the Grafana `data` folder now, in Zolai Admin after
  Phase 8; no Superset/Metabase work is scheduled.
- Planned metrics (`zolai_quality_failures_total`, `zolai_worker_jobs_total`,
  `zolai_queue_depth` — [observability §1.1](../architecture/observability.md)) are the raw
  material for the data class; they still land in Prometheus first (operational), and the
  *analytical* views read the DB tables — different stores, no panel duplication.
- The ownership matrix is recorded in
  [observability §7](../architecture/observability.md#7-dashboard-ownership-matrix)
  so every new dashboard cites its owner.
- BI need stays **needs-founder** (UNKNOWN): if a community analyst appears before Phase 8,
  the interim can be the Grafana `data` folder with read-only share rather than an early
  Metabase deploy.

## Rejected alternatives

- **Superset now:** DEFER — 4-part stack (verified, matrix §7) for zero BI consumers; revisit
  only if governance-heavy BI (certified datasets, row-level governance) becomes the need.
- **Metabase now:** DEFER — single container makes it the **pre-approved first pick** at the
  trigger, but AGPL + Pro-gated SSO/RLS and still no consumer; not justified yet.
- **Data dashboards in Grafana permanently:** rejected — mixes analytical views into the
  operational tool and re-creates the duplication the constraint forbids once admin/BI arrive.
- **Ad-hoc SQL forever:** rejected as the *decision* (it remains the fallback for one-off
  questions) — no shared, persistent data-dashboard home means results are not reproducible
  for a second person.

## Migration implications

- Interim → target hand-off (Phase 8): Grafana `data` folder panels are re-expressed once in
  Zolai Admin analytics; the folder is then retired, not kept in parallel (no dual ownership).
- If the BI trigger fires: deploy Metabase (or Superset) pointed at read-only views/replica,
  migrate the *data* class only, and record the flip as an amendment to this ADR — Grafana
  and the admin AI/RAG views are untouched.
- Metric/dashboard additions must name their owner class at creation time (observability §3
  parity rules still apply to anything operational).
