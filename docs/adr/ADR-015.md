# ADR-015: Migrate-not-rename schema governance

## Context

The canonical DB has 105 live tables (2026-09-29), documented at 101, with known
consolidation candidates already listed in `tables.md` (e.g. `vocabulary` vs
`zolai_vocabulary`, `grammar_patterns` vs `zolai_grammar_patterns`, `word_usage` vs
`zolai_word_usage`, `proverbs` vs `zolai_proverbs_idioms`) and 26 `*_import` staging
tables pending a PROPOSED archive plan. Schema evolution so far follows good instincts —
additive, idempotent DDL (`eval_sets`/`eval_cases` created with `CREATE TABLE IF NOT
EXISTS`, leaving existing tables untouched) and a `migrations.py` with 27 constraints +
50+ indexes. The PostgreSQL move (ADR-001) will be the largest schema event in the
project's life, and ad-hoc renaming during it would be silently catastrophic: downstream
code, docs, dashboards, eval payloads, and exports all reference table/column names.

## Problem

Without a governance rule, three failure modes recur: (1) **blind renames** — someone
"cleans up" a name and breaks readers nobody remembered (Python modules, JSON payloads,
Grafana queries, MCP answers, docs); (2) **unversioned, unreviewed DDL** applied straight
against the live 2.3 GB DB with no dry-run; (3) **doc/DB drift** — schema changes that skip
`tables.md`/catalog updates (already happening: 101 vs 105). Any of these during the
SQLite→Postgres dual-run would make parity checks meaningless.

## Options

1. **Governance rule: migrate-not-rename; additive-first; explicit OLD→NEW mapping docs;
   versioned migrations; mandatory backup→checksum→dry-run→apply→verify** (recommended).
2. Ad-hoc edits + hope (status quo risk).
3. Big-bang rebuild/rewrite of the schema during PG cutover.
4. Adopt a heavy schema-migration platform (migration SaaS / heavy framework).

## Decision

**Migrate-not-rename schema governance (standing rule):**
- **No blind renames.** A rename requires an explicit OLD→NEW mapping entry (table-level and
  column-level), a compatibility window (old name kept as view/copy or dual-read), and doc
  updates in the same change.
- **Additive-first:** new tables/columns first (`CREATE TABLE IF NOT EXISTS` idempotent DDL,
  the existing pattern); destructive steps only after readers are dual-running.
- **Versioned migrations:** every schema change is an ordered, reviewable migration file
  (extending `migrations.py` conventions), never hand-run one-off DDL against prod.
- **Mandatory sequence for any data change:** **backup → checksum → dry-run → apply → verify.**
- **Docs in lockstep:** `tables.md`/catalog ([ADR-004](ADR-004.md)) regenerate in the same
  change — closing gap G14 permanently.

## Reasons

- **Constraints demand it:** versioned migrations, backup before data migrations, and the
  plan's "OLD→NEW mapping (no blind renames)" are explicit client constraints.
- **Provenance requires stable identity:** the provenance chain must answer "which dataset
  version / which table did this come from" — renames without mapping sever lineage.
- **Dual-run viability:** parity between SQLite and Postgres ([ADR-001](ADR-001.md)) is only
  checkable if both sides agree on names; mapping-driven migration keeps parity honest.
- **The additive pattern already works here** (eval tables) — this codifies it rather than
  inventing process.
- **Cheap to follow, expensive to ignore:** a mapping markdown + migration files + backup
  discipline cost minutes; archaeology after a blind rename costs days.

## Consequences

- Every schema PR includes: migration file(s), OLD→NEW mapping row (if any rename/move),
  regenerated docs, and a rollback note (how to restore from the pre-change backup).
- Some names will be *kept* even when ugly, until a mapped compatibility window is run —
  cosmetic renames are explicitly deprioritized.
- Consolidation candidates in `tables.md` become mapped merge operations (e.g.
  `zolai_vocabulary` ← `vocabulary`) executed as: new structure + dual-write/backfill +
  verify counts + deprecate old reader — never an in-place swap.
- Backup volume grows (pre-change snapshots of a 2.3 GB DB) — Phase 0 baseline and
  retention policy (batch 2 lifecycle doc) must accommodate it; checksums make restores
  verifiable.
- PG cutover inherits the rule: mapping document is the Phase 2 deliverable; cutover
  (Phase 4) is founder-gated ([ADR-001](ADR-001.md)).

## Rejected alternatives

- **Blind/ad-hoc renames:** rejected outright — the failure mode this ADR exists to prevent.
- **Big-bang schema rebuild during cutover:** rejected — unverifiable parity, high blast
  radius on the one dataset the project cannot recreate.
- **Status quo (unversioned DDL):** rejected — works by luck at current change rates;
  unacceptable during migration phases.
- **Heavy migration platform/SaaS:** rejected — our migration needs are plain SQL +
  Python conventions already in-tree; adding a platform violates zero-new-infra.

## Migration implications

- **Phase 0:** backup + checksum baseline (establishes the verify primitive).
- **Phase 2:** OLD→NEW mapping doc for SQLite→Postgres, reviewed before any code moves —
  every consolidation candidate resolved into an explicit mapped decision.
- **Phases 3–9:** all subsequent DDL (quality tables, catalog tables, `pipeline_runs`,
  RBAC/keys, versioning, `rag_traces`) follows this ADR's sequence; each ships additive
  first.
- **Rollback universal pattern:** restore pre-change backup → verify checksums → re-apply
  fixed migration; no operation proceeds without that path documented.
