# ADR-017: Dataset lifecycle — immutable publish with version bump

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-30 |
| Decision owner | founder |
| Decision | **CONFIGURE draft → validated → published → deprecated; published = immutable snapshot, corrections = new `major.minor.patch` version** |
| Revisit when | A consumer genuinely needs mutable "latest" datasets (none does: training/RAG/eval all pin versions) |
| Evidence | [Dataset lifecycle §1–3](../data/dataset-lifecycle.md) · [Versioning §2](../data/versioning.md) · [ADR-005](ADR-005.md) · [ADR-007](ADR-007.md) |

## Context

Published datasets must be **immutable with checksums** — a core project constraint — and
[ADR-007](ADR-007.md) already decided the storage mechanics (`manifest_sha256`,
`dataset_versions` insert-only rows). What was still only prose is the **state machine**:
how a candidate becomes published, what may still change in each state, and how corrections
happen. [Dataset lifecycle](../data/dataset-lifecycle.md) specifies exactly that; this ADR
formalizes it as a decision so it is testable and citable (status PROPOSED there → enforced
starting Phase 9).

## Problem

Without a declared lifecycle, datasets exist as folders/exports with no state rows: any edit
silently invalidates every checksum, pin, and downstream eval that referenced "the dataset".
Consumers (zolai-training, the RAG index, eval runs) need a promise — *the bytes behind a
published version never change* — plus a defined correction path so that promise is not
circumvented by "we'll just fix it in place".

## Options

1. **Four-state lifecycle with immutable publish + semantic version bump** (recommended —
   formalizes the delivered design).
2. Mutable "latest" datasets with timestamps only (status quo, generalized).
3. Git-branch/tag semantics for datasets (branch → draft, tag → published).
4. Defer the whole lifecycle until Postgres cutover.

## Decision

**CONFIGURE the four-state lifecycle; keep published data immutable; corrections create new
versions.** Tags: **CONFIGURE** (enforcement Phase 9).

- **States:** `draft` (freely mutable) → `validated` (quality run PASS + review) →
  `published` (**immutable**, manifest + checksum) → `deprecated` (advisory flag; rows stay).
  Abandonment from `draft` is audited, never deleted.
- **Publish gate (all five, no partial publish):** quality run PASS with zero blocker
  failures ([ADR-005](ADR-005.md)) · checksum computed · provenance complete
  ([ADR-018](ADR-018.md)) · `data_audit_log` row · actor holds `dataset:publish`
  ([ADR-010](ADR-010.md) — founder-held in v1).
- **Corrections:** copy forward to a new draft (`supersedes_version_id` set) and bump
  **major** (breaking structure) / **minor** (content change) / **patch** (metadata only) —
  same rules as [lifecycle §3](../data/dataset-lifecycle.md#3-corrections-create-new-versions).
- **State history is append-only:** every transition writes a `dataset_versions` change *and*
  an audit row (who, why, when).

## Reasons

- **Immutability is only meaningful with a defined correction path** — otherwise pressure to
  fix data will break the rule; a version bump makes the fix legal and traceable.
- **Reuses mechanics that already exist** — `dataset_versions` columns already carry `state`,
  `manifest_sha256`, `quality_run_id`, `supersedes_version_id`
  ([versioning §2](../data/versioning.md)); this ADR adds no new mechanism.
- **Consumer pinning depends on it:** training pins `dataset_versions.id` + manifest hash,
  eval runs pin set + version, the desktop bundle pins a snapshot hash — all assume published
  bytes never move.
- **RBAC fits naturally:** validate/publish/deprecate are distinct actions, so the highest
  privilege (`dataset:publish`) stays with one holder instead of being implied by edit rights.

## Consequences

- Publish becomes a ritual with mandatory evidence (quality run id + manifest hash + audit
  row); "publishing on partial information" is a gate failure, not a judgment call.
- Every data-changing pipeline treats published versions as read-only; fixes flow through
  `draft` of vN+1 ([workflows §1](../admin/workflows.md#1-publish-dataset-draft--validated--published)).
- Staging (`*_import`) rows are archived, never deleted; deprecation replaces deletion
  ([lifecycle §5](../data/dataset-lifecycle.md#5-deprecation-vs-deletion)).
- Enforcement is Phase 9 work: immutability guards (triggers/app-level checks) need both
  SQLite and Postgres dialect variants ([ADR-015](ADR-015.md)).

## Rejected alternatives

- **In-place updates of published rows:** rejected — destroys checksums, breaks every pin,
  and violates the immutability constraint outright.
- **Mutable "latest" datasets:** rejected — no reproducibility for training/eval; a "latest"
  pointer is allowed only as a *name* that resolves to an immutable version id.
- **Git branch/tag semantics:** rejected — large data never enters Git
  ([overview §5](../architecture/overview.md#5-invariants-standing-rules--violations-block-merge));
  manifests + DB rows give the same semantics without blobs in the repo.
- **Deferring until Postgres:** rejected — immutability is a workflow rule, not a dialect
  feature; SQLite can enforce it now and the rule transfers unchanged.

## Migration implications

- Phase 9 (provenance/immutability/versioning): add state rows for existing datasets —
  **backfill is additive and founder-gated** (today most datasets have no state; bulk
  promotion to `published` requires the same backup → checksum → dry-run → apply → verify
  discipline as any data change).
- Corrections to already-published exports follow the new-draft path from day one; nothing is
  re-written retroactively.
- Postgres cutover ([ADR-001](ADR-001.md)) is neutral: the state machine lives in tables;
  only immutability guard implementation differs per dialect.
