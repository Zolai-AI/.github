## Context

RAG quality is currently gated **DB-first**: `eval_sets`/`eval_cases`/`eval_runs` are
tables, `zolai-eval` runs gates, and `/api/metrics/eval` + Grafana surface pass/fail —
verified local architecture. What's missing: per-request RAG traces (query, retrieved
chunks, prompt, answer, scores) — gap G12. The LLM-observability market verified
2026-09-29: **Langfuse** = MIT core (`ee/` dirs commercial), self-host runs PG +
ClickHouse + Redis + S3-compatible storage ("4-service" shape: unverified — secondary
source; MIT + ClickHouse architecture verified), acquired by ClickHouse Jan 2026 with MIT
stated unchanged; **Arize Phoenix** = **Elastic License 2.0**, single container on
SQLite/Postgres; **Opik** = Apache 2.0 (comet.com); **Dynatrace to acquire Arize**
(Aug 2026 — unverified — secondary source, Langfuse comparison page).

## Problem

When a RAG answer degrades, we can currently see *that* a gate failed (`eval_runs`) but not
*why* — which chunks were retrieved, what the prompt contained, how the rewrite behaved.
Standing up Langfuse now would add four services for a low-traffic system whose regression
detector (evals) already exists. Doing nothing means debugging by ad-hoc logging. We need a
middle path: trace storage in our own DB, deferring external platforms to a sharp trigger.

## Options

1. **DB-first `rag_traces` table + richer eval runs; defer platforms** (recommended).
2. Self-host Langfuse now.
3. Self-host Phoenix now.
4. Self-host Opik now.
5. Vendor SaaS (Langfuse Cloud / Arize AX) — data leaves the host.

## Decision

**CONFIGURE DB-first `rag_traces` + eval; DEFER Langfuse/Phoenix.**
Tags: **BUILD/CONFIGURE** `rag_traces` (additive DDL) + trace capture at answer time
(sampling/size-capped) + eval linkage; **DEFER** all external observability platforms;
**Opik** noted in the matrix as the most permissive alternative (Apache 2.0) if a platform
is ever needed.

## Reasons

- **Eval gates today** — the primary regression detector exists; traces are a debugging
  amplifier, not the detector itself.
- **DB-first fits every constraint:** no new service, provenance lives beside the data,
  Grafana already renders our DB-derived metrics (extend ADR-002's stack).
- **Langfuse's self-host shape is the most expensive option on the list** (PG+CH+Redis+S3 —
  stack-shape claim unverified — secondary source; MIT verified) — wildly disproportionate
  at current traffic.
- **Phoenix is the lightest external option** (single container; ELv2 verified) and is
  therefore pre-approved as **first** external pick at the trigger — same pre-decision
  pattern as Label Studio in ADR-011.
- **License awareness:** Phoenix's ELv2 bars offering it as a managed service (verified
  via Langfuse comparison page) — fine for internal use, but another reason DB-first is
  the default.

## Consequences

- `rag_traces` schema decisions: capture keys (trace id, question, top-k chunk ids +
  scores, prompt hash, answer, latency, model, eval linkage), retention policy (size caps /
  pruning — traces are bulky), and sampling (log 100% of eval traffic, sampled % of live).
- Trace capture must be cheap and failure-isolated: a trace write must never fail an answer.
- Debugging workflow shifts from "open Langfuse UI" to SQL queries + Grafana panels over
  trace aggregates — acceptable while traffic is single-node/low.
- Slight duplication risk with `eval_runs` metrics — mitigated by explicit linkage columns
  (traces reference eval run ids and vice versa).

## Rejected alternatives

- **Langfuse now:** DEFER — 4-service self-host (shape unverified — secondary source);
  revisit if/when team-grade production monitoring is needed (and by then its ClickHouse
  backing may reduce ops cost).
- **Phoenix now:** DEFER — lightest option, but still a service with no measured need yet;
  **pre-approved first at trigger** (RAG regressions untraceable from evals).
- **Opik:** noted only — Apache 2.0 makes it the license-cleanest platform; adoptable at
  any trigger (matrix §12).
- **Vendor SaaS:** rejected — internal corpus/questions leave the host; unnecessary.

## Migration implications

- Additive DDL only (`CREATE TABLE IF NOT EXISTS rag_traces` + indexes), mirroring the
  eval-store pattern — portable to Postgres unchanged ([ADR-001](ADR-001.md);
  [ADR-015](ADR-015.md)).
- Phase 9/10 of the roadmap covers provenance + observability extension; trace retention
  interacts with backup sizing (Phase 0 baseline) — document retention in the data-lifecycle
  doc (batch 2).
- If Phoenix trigger fires: side-by-side run (emitters fan out to DB + Phoenix via OTLP-style
  export) before any cutover — no big-bang switch.
