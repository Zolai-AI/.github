# ADR-009: Custom thin Next.js admin in zolai-web

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-29 |
| Decision owner | founder |
| Decision | **BUILD thin custom Next.js admin in zolai-web** |
| Revisit when | CRUD >30 generic resources → Refine inside Next.js |
| Evidence | [Tool matrix §11](../research/data-platform-tool-matrix.md) · [Current-state gap G9](../architecture/current-state.md) |

## Context

Operators need UIs for **domain workflows**: POS batch review, quality-run inspection,
dataset publish, eval-regression triage, audit browsing. zolai-web is already a Next.js app
with Prisma (66 models), session auth (`User`/`Session`/`Account`/`TwoFactor`), and audit
models (`AuditLog`, `SecurityEvent`). Nothing admin-shaped exists today (gap G9). The admin
tooling market in 2026: **Directus relicensed to MSCL-1.0-GPL at v12 (May 2026)** with
license enforcement gating SSO/custom permission rules (verified: directus.com + v12.0.0
release, 2026-09-29); **React-Admin is MIT-core but `ra-rbac` and `ra-audit-log` are paid
EE modules** (verified: GitHub LICENSE.md + marmelab EE docs); **Refine is MIT**
(verified: refine.dev license page); **AdminJS's last release was v7.8.17 on 2025-07-15**
with open maintenance-status concerns (verified: releases + issue #1801).

## Problem

Linguistic workflows (review a POS batch against corpus context, run quality rules, publish
an immutable dataset, inspect an eval regression) are **domain-UX problems**, not generic
CRUD problems. Off-the-shelf admins give generic tables and would need: a second service
(Directus), paid licenses for the exact features we need (React-Admin EE RBAC/audit), or an
abstraction layer that fights our custom views (generic frameworks) — while the app that
should host this UI already exists.

## Options

1. **Thin custom admin section inside zolai-web (Next.js routes + components)**
   (recommended).
2. Directus as a separate admin service.
3. React-Admin embedded (MIT core, EE for RBAC/audit).
4. Refine embedded (MIT).
5. AdminJS.
6. No admin UI (scripts only).

## Decision

**BUILD thin custom Next.js admin in zolai-web.**
Tags: **BUILD** admin routes/components on the existing app; reuse Prisma + session auth +
action RBAC ([ADR-010](ADR-010.md)); **REJECT** Directus and AdminJS; **DEFER** Refine as
explicit fallback if generic CRUD explodes (>30 resources); React-Admin not preferred.

## Reasons

- **Domain UX on existing foundations:** workflows need purpose-built screens over tables
  we already model in Prisma — no new API surface, no new auth system, no new deployment.
- **RBAC day-1:** admin actions map onto the same action-based permission model being built
  for the platform ([ADR-010](ADR-010.md)) — one authorization story, not two.
- **Auditability for free-ish:** `AuditLog`/`data_audit_log` are already in place; admin
  actions write to them (human corrections auditable — constraint).
- **Zero new services** — stays inside the v1 container budget (0–1 new containers).
- **License safety:** avoids MSCL restrictions and paid-EE gating of RBAC/audit features.

## Consequences

- We own the UI code: forms, tables, and states for each workflow (the admin IA, workflows,
  and permission matrix live in batch-2 docs under `docs/admin/`).
- "Thin" is a discipline: admin pages call existing APIs/Prisma actions; no business logic
  duplicated in the UI layer.
- Generic features (filters, pagination, bulk actions) must be built as small shared
  components — this is the maintenance cost of not adopting a framework.
- The fallback discipline: if a long tail of simple CRUD resources accumulates (>30),
  introduce Refine inside Next.js for those screens only (mixed approach), per the revisit
  trigger.

## Rejected alternatives

- **Directus:** **REJECT** — MSCL-1.0-GPL since v12 (May 2026) + license enforcement on
  SSO/custom rules + it is a second service with its own Postgres-facing data layer
  (duplication risk with our canonical DB).
- **React-Admin:** not preferred — RBAC and audit-log, precisely our must-haves, sit behind
  paid EE (€145+/mo); MIT core alone doesn't cover them.
- **Refine:** DEFER — MIT is clean, but adding a framework now precedes the CRUD-explosion
  evidence; it remains the sanctioned fallback.
- **AdminJS:** **REJECT** — stale (last release Jul 2025 verified) with community-reported
  maintenance gaps and unpatched vulnerabilities in plugins (issue #1801 replies).
- **Scripts-only:** rejected — review/publish workflows need non-engineer operators eventually
  and gap G9 is Medium.

## Migration implications

- Admin screens read through the versioned API where one exists (`/api/v1`, ADR-014) and
  through server actions/Prisma for internal-only paths — keeping the Postgres cutover
  ([ADR-001](ADR-001.md)) transparent to the UI (Prisma is already Postgres).
- Phase 8 of the roadmap: admin v1 lands together with RBAC/API-keys so every admin action
  is permissioned from day one.
- If Directus/Refine decisions are revisited, screen inventory (IA doc, batch 2) defines
  what must be re-implemented — a bounded migration list.
