# ADR-010: Action-based RBAC + API keys

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-29 |
| Decision owner | founder |
| Decision | **BUILD action-based RBAC (Prisma Role/Permission) + API keys; DEFER IdP/SSO** |
| Revisit when | First external role or SSO requirement → managed IdP (Auth.js providers first) |

## Context

"RBAC day 1" is a stated constraint. zolai-web's Prisma schema already carries identity and
security models (`User`, `Session`, `Account`, `TwoFactor`, `AuditLog`, `RateLimit`,
`SecurityEvent`, `LoginHistory`, `Backup`), and the platform brief refers to existing
Role/Permission models. On the zolai-core API side, **no API-key auth exists** — a grep of
`zolai/api/server.py` found none, matching the long-standing PENDING note ("API-key auth +
per-key/organization limits") in `context/progress-tracker.md`. This is the platform's
only **Critical** access gap (G2/G3).

## Problem

Today every caller of the zolai-core API is effectively trusted: there is no per-caller
identity, no key revocation, no rate/organization limits, and no enforced mapping of
"who may publish a dataset / run a quality gate / edit a POS batch". As the admin UI
(ADR-009) and MCP consumers come online, actions need permissions — but standing up an
external IdP now (Keycloak/Ory) would add services for a single-operator system that merely
needs role-scoped actions and machine keys.

## Options

1. **Action-based RBAC on existing Prisma Role/Permission models + API keys for
   zolai-core** (recommended).
2. Deploy Keycloak/Ory as the IdP immediately.
3. Embed Casbin-style authorization library with custom model.
4. Role-check middleware only (coarse roles, no action granularity).
5. No auth (status quo) — rejected by constraint.

## Decision

**BUILD action-based RBAC (Prisma Role/Permission) + API keys; DEFER IdP/SSO.**
Tags: **BUILD** (a) role × action permission matrix wired to Prisma models for zolai-web
incl. admin; (b) API-key issuance/scopes/rotation for zolai-core; **DEFER** Keycloak/Ory/
Casbin-as-service and SSO to the trigger (Auth.js providers attempted first when SSO
arrives).

## Reasons

- **RBAC is a day-1 constraint and the models exist** — the work is mapping actions to
  permissions, not inventing storage: permission = `(subject, action, resource-class)` rows,
  checked at the edge of admin/API entry points.
- **Action-based beats role-sprawl:** roles are just named bundles of action grants
  (e.g. `data_steward` = `dataset.publish`, `quality.run`, `pos.review`), so fine-grained
  policy changes don't require new role explosion.
- **API keys solve the machine-caller problem immediately:** MCP server, desktop app, and
  pipelines authenticate with keys carrying scopes + per-key/org limits (closing the known
  PENDING gap) — no user session machinery for machines.
- **One authorization story** across web (session subject) and core API (key subject) —
  same action vocabulary, shared enforcement patterns.
- **Zero new services** — everything lives in the two existing data stores.

## Consequences

- A canonical **action list** must be defined and frozen (e.g. `dataset.publish`,
  `dataset.read`, `quality.run`, `eval.inspect`, `pos.review`, `user.manage`,
  `audit.read`, `settings.write`) — this is the contract for admin (ADR-009) and API
  (ADR-014) work; full matrix lands in `docs/admin/permissions.md` (batch 2).
- Enforcement code must exist at **every** entry point; routes added later without
  permission checks are regressions — a checklist/test obligation.
- Key management adds operational surface: issuance UI/page, hashed storage, scopes,
  revocation, rotation policy, and rate limits per key (design in batch 2).
- Every denied/allowed admin action should emit an audit event (ties to `AuditLog` +
  `data_audit_log` philosophy — human corrections and admin actions auditable).
- Migration of existing users/scripts to keys must be coordinated (grace period).

## Rejected alternatives

- **Keycloak/Ory now:** DEFER — external IdP = new service(s); revisit at first external
  org role or hard SSO requirement; Auth.js providers (Google/GitHub OAuth) precede a full
  IdP.
- **Casbin now:** DEFER — an in-process library still needs a policy schema; our action
  matrix in Prisma is simpler today. Casbin may implement checks later if policy complexity
  grows.
- **Coarse role-checks only:** rejected — insufficient granularity for publish/quality/POS
  distinctions demanded by the admin workflows.
- **Status quo (no authz):** rejected — violates the RBAC-day-1 constraint; G2/G3 Critical.

## Migration implications

- Phase 8 of the roadmap ships RBAC + API keys + admin v1 together (so no unpermissioned
  admin actions ever exist).
- Existing API consumers get keys before enforcement flips on (dual-accept window, then
  enforce).
- Postgres cutover ([ADR-001](ADR-001.md)) moves permission tables with everything else;
  no rename dependencies ([ADR-015](ADR-015.md)).
- SSO future: when triggered, identities externalize but action grants remain ours — IdP
  supplies the subject, RBAC supplies the verbs (no rewrite).
