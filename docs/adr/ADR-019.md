# ADR-019: RAG evaluation — DB-first eval sets/runs as the quality gate

| Evidence | [Evaluation §1–5](../pipelines/evaluation.md) · [Tool matrix §12](../research/data-platform-tool-matrix.md) · [ADR-005](ADR-005.md) · [ADR-012](ADR-012.md) |

## Context

RAG/answer quality must be gated **early** (evaluation runs before product polish), and the
store already exists: `eval_sets` (3 sets), `eval_cases` (273 cases, payload verbatim),
`eval_runs` (append-only history), the `zolai-eval` CLI, `/api/metrics/eval`, and a Grafana
eval panel — all **EXISTS** and DB-first ([evaluation §1–§2](../pipelines/evaluation.md)).
[ADR-012](ADR-012.md) separately decided *observability* (traces stay in-DB, platforms
deferred). What this ADR formalizes is the **evaluation decision**: which datasets gate what,
how a regression fails a build, and that vendor eval/observability suites do not own this
lane. Data quality is a *different* lane ([ADR-005](ADR-005.md)) — the two are never merged
into one score.

## Problem

Without a declared evaluation decision, three things drift: (a) eval sets get edited with the
same casualness as data (eval-set drift is one of the three regression classes), (b) gate
failures are treated as advisory because no threshold is owned, and (c) pressure arrives to
"just use Langfuse/Phoenix evals" — re-implementing in a platform what our tables already do.
We need the datasets, the gate rule, and the ownership of its one open parameter recorded.

## Options

1. **DB-first eval sets + gated runs with an explicit regression rule** (recommended —
   formalizes the delivered design).
2. Vendor eval platform now (Langfuse/Phoenix eval modules).
3. Metrics recorded, no gate (advisory dashboards only).
4. Merge eval score with data-quality score into one gate.

## Decision

**CONFIGURE the DB-first eval lane with a regression gate; DEFER vendor eval platforms.**
Tags: **CONFIGURE** (policy) / **KEEP** (existing store).

- **Datasets of record:** `smoke` (36 cases, per-PR CI), `eval_v1` (110, nightly),
  `benchmark_qa` (127, release candidate/weekly). Each run writes an `eval_runs` row with
  `source = ci|cron|manual|release`; runs are **never updated or deleted**.
- **Gate rule R-EVAL-1 (draft):** a gated run fails when a tracked metric drops below
  `baseline − threshold`, baseline = best `gate_passed=true` value over the trailing window
  (last 10 passing runs).
- **Threshold: needs-founder.** Default proposal = **absolute F1 drop > 0.02** (or > 5%
  relative, whichever is stricter); until the founder sets `eval_gate_threshold`, CI runs the
  gate **advisory** — gate runs, no hard fail ([evaluation §4](../pipelines/evaluation.md)).
- **Scope:** per-task F1 (exact-match where F1 is undefined); intentional trade-offs go
  through a `settings:write` + audit waiver — never by editing past `eval_runs`.
- **Separation invariant:** quality gates gate *data publish*; eval gates gate *model/answer*
  changes. Both may be required to ship a combined release; neither excuses the other.

## Reasons

- **The store, CLI, metrics endpoint, and dashboard already exist** — the decision costs
  nothing to honor and protects a working asset from tool churn.
- **Append-only run history is the regression detector:** triage (data / code / eval-set
  change) reads `eval_runs` + `pipeline_runs.git_sha` + audit rows in one place.
- **The threshold is a language-accuracy tolerance, not an engineering constant** — hence
  `needs-founder` rather than an invented number; the 0.02 default gives CI something
  concrete to standardize on once signed.
- **Vendor platforms lose on fit today:** Langfuse self-host is a 4-service shape (PG +
  ClickHouse + Redis + S3 — unverified claim, secondary source; MIT verified); Phoenix is
  ELv2 single-process and pre-approved *first at the trace trigger*, not as an eval owner.
- **No merged score** — a single blended number would hide a data regression behind a model
  win (and vice versa), which is exactly what the split-lane invariant forbids.

## Consequences

- Eval-set edits require review discipline equal to data edits (eval-set drift is a named
  regression class); `eval_cases` diffs are inspected before merge.
- CI wiring (Phase 7/10): PR-time `smoke`, nightly `eval_v1`, release `benchmark_qa` — each
  writing `eval_runs` and surfacing via `/api/metrics/eval`.
- The one open parameter (`eval_gate_threshold`) is tracked as **needs-founder**: the doc row
  flips to CONFIRMED with a date when the founder sets it in settings.
- If gating proves insufficient (e.g. human preference judging needed), the revisit path is
  the ADR-012 trace trigger (Phoenix first) — not a silent replacement of the eval store.

## Rejected alternatives

- **Langfuse/Phoenix eval modules now:** DEFER — re-implements an existing store behind a
  service; platforms stay deferred per [ADR-012](ADR-012.md) (Phoenix pre-approved first at
  *its* trigger).
- **Metrics without a gate:** rejected — records history nobody is obliged to act on; the
  known failure mode is shipping silent regressions (the reason evaluation "must be built
  early").
- **Merging data quality and model quality into one score:** rejected — violates the
  standing separation ([quality §6](../data/quality.md#6-data-quality--model-quality--no-single-score)).
- **Hard-coded permanent threshold:** rejected in both directions — an unsigned 0.02 that
  hard-fails CI can block legitimate data updates; no threshold at all lets real regressions
  ship. Advisory-until-signed is the middle path.

## Migration implications

- Policy lands in Phase 7/10 (CI/cron wiring) — **no schema change**: `eval_sets`,
  `eval_cases`, `eval_runs` already exist; planned additive link `dataset_version_id` on runs
  joins the lane to [ADR-017](ADR-017.md)/[ADR-018](ADR-018.md) lineage (Phase 9).
- Postgres cutover ([ADR-001](ADR-001.md)) is neutral — tables are portable; gate logic lives
  in the `zolai-eval` CLI.
- Waivers change `settings` only, with audit events; historical runs are immutable under all
  migrations.
