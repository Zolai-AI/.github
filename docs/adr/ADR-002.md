# ADR-002: Keep the just-built Prometheus + Grafana metrics stack

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-29 |
| Decision owner | founder |
| Decision | **KEEP Prometheus 3.15 + Grafana 13.2.3 + REST metrics** |
| Revisit when | Never — unless Grafana licensing posture changes |
| Evidence | `zolai-core/docs/MONITORING.md` (local) · [Tool matrix §9](../research/data-platform-tool-matrix.md) |

## Context

A full metrics stack was just built and is running: `docker-compose.monitoring.yml`
with **Prometheus 3.15.0** and **Grafana 13.2.3**, instrumentation under
`zolai/monitoring/` (pinned `prometheus-client==0.26.0`), an 11-endpoint REST surface in
`zolai/api/metrics_router.py` mounted before the catch-all route, three provisioned
dashboards (`api-overview`, `database-storage`, `linguistic-pipeline`), three alert rules
in `zolai/monitoring/alerts.py::RULES` (http error rate, http p95 latency, db p95 latency),
and a **parity gate test** (`tests/test_alert_rules_parity.py`) that keeps `RULES` ↔
Prometheus rule files ↔ Grafana `rules.yml` in lockstep. Grafana annotation push from the
API is wired (`POST /api/metrics/annotations`).

## Problem

Temptation exists to swap components ("newer", "more standard", cheaper TSDBs) or to bolt
on additional observability vendors. Replacement would discard working dashboards, the
annotation pipeline, the alert-parity gate, and weeks of tuning — violating the project
constraint **"do not rewrite working systems without evidence"** and the
**"extend don't replace"** rule for already-built infrastructure.

## Options

1. **KEEP as-is** and extend only when gaps are proven (recommended).
2. Replace with VictoriaMetrics + alternative dashboards.
3. Replace with a managed SaaS observability vendor.
4. Add parallel/overlapping monitoring (second metrics system) — duplication.

## Decision

**KEEP Prometheus 3.15 + Grafana 13.2.3 + REST metrics.**
Tag: **CONFIGURE** any additions onto this stack (new metrics, dashboards, alert rules go
through the existing parity gate). No replacement, no parallel system.

## Reasons

- **Just built** — evidence-driven constraint: nothing is broken; there is no measured pain.
- **Alert parity gate exists** — a rare, working safeguard; rebuilding it elsewhere is cost
  with no benefit.
- **REST surface already serves** health/eval/performance/alerts to operators and Grafana;
  `/api/metrics/eval` already surfaces `eval_runs` gate status.
- **Licensing is fine for internal use:** Prometheus is Apache 2.0 (unverified — official
  LICENSE URL cited, not fetched); Grafana core is AGPLv3 since 2021 (**verified**
  grafana.com/licensing, 2026-09-29) — AGPL is acceptable for internal, non-embedded use.
- **Duplication constraint:** adding Superset/OpenMetadata-style overlays or a second
  metrics stack was explicitly forbidden; keeping one stack satisfies it.

## Consequences

- Metric naming (`zolai_<domain>_<metric>`) and the pin on `prometheus-client==0.26.0`
  become conventions new code must follow.
- Every new alert rule must be added in all three places (code, Prometheus files, Grafana
  provisioning) or CI parity fails — by design.
- If Grafana ever changes licensing posture adversely, a deliberate migration decision
  (new ADR) is triggered; that is the only listed revisit trigger.
- Business/corpus metrics (`zolai_corpus_sentences`, `zolai_dictionary_entries`, …) continue
  to be the operational view of data health — analytical BI stays a separate concern
  (ADR for analytics: see matrix §7; Grafana `data` folder interim).

## Rejected alternatives

- **VictoriaMetrics swap:** rejected — replacing a working stack without evidence violates
  "extend don't replace".
- **Managed SaaS observability:** rejected — cost, data egress of internal metrics, and no
  demonstrated need.
- **Second/parallel metrics system:** rejected — duplication constraint.
- **No monitoring at all:** rejected — the stack exists and gates alerting.

## Migration implications

- No migration; the obligation is **preservation**. Version bumps of Prometheus/Grafana go
  through the compose file and re-run the parity test before merge.
- If a future phase adds business-quality metrics (rule-pass rates from ADR-005's harness),
  they are **added** to this stack — new gauges + one dashboard row + parity entries —
  never exported to a separate tool.
