## Context

The zolai-core FastAPI surface has **~52 direct routes** on `server.py` (mostly unversioned
legacy paths), plus a **`foundation_router` already mounted at `/api/v1`** (22 routes) and
an 11-endpoint `metrics_router`. Consumers: `zolai-mcp-server` (Cloudflare Workers proxy),
`zolai-tauri` (offline desktop), scripts, and zolai-web where applicable. Critically, a
grep of `server.py` found **no API-key authentication** — confirming the PENDING gap
tracked in `context/progress-tracker.md` ("API-key auth + per-key/organization limits").
CORS/metrics are open by design for the monitoring stack; there is no per-caller identity
anywhere on the core API.

## Problem

Two coupled problems: (1) **no authentication/authorization** on a public-facing API — every
caller is trusted, there is no revocation, no per-key or per-org limits, and no way to
distinguish MCP traffic from desktop traffic from scripts; (2) **no versioning discipline**
— when behavior must change, unversioned routes break every consumer at once, and the
half-done `/api/v1` prefix means new and old styles coexist unpredictably. Together they
block external integrations, RBAC enforcement (ADR-010), and safe evolution.

## Options

1. **Freeze + finish `/api/v1` as the canonical surface; add API-key auth (scopes, hashed
   keys, per-key/per-org limits); legacy routes deprecated on a schedule** (recommended).
2. Auth only, no versioning (keep breaking routes when needed).
3. Versioning only, no auth (status quo security).
4. Immediately require OAuth/OIDC via a deployed IdP (Keycloak/Ory) instead of API keys.
5. mTLS or IP-allowlist only — poor fit for MCP/desktop/script diversity.

## Decision

**BUILD action-based RBAC (Prisma Role/Permission) + API keys; DEFER IdP/SSO** — applied to
the API as: **BUILD `/api/v1` versioning discipline + API-key auth** on zolai-core.
Tags: **BUILD** key issuance/storage/scopes/limits + auth middleware; **CONFIGURE** the
`/api/v1` prefix as canonical (extend the existing foundation-router pattern), mark legacy
routes deprecated, document contract; **DEFER** IdP/SSO to its trigger.

## Reasons

- **Closes the known P0 gap:** API keys are the minimal correct auth for machine callers
  (MCP, desktop, scripts): revocable, scopeable, rate-limitable — without session/OIDC
  machinery.
- **The `/api/v1` prefix already exists** — this is finishing an in-flight pattern, not a
  new convention (**extend, don't rewrite**).
- **Versioning makes RBAC and changes safe:** permission checks and behavioral changes land
  behind `/api/v1`, so consumers migrate deliberately.
- **Scales to the RBAC model:** keys carry scopes; user sessions (web/admin) carry
  role-grants — both resolve to the same action vocabulary ([ADR-010](ADR-010.md)).
- **No popular-tool bias / no new services** — middleware in the existing FastAPI app,
  key hashes in the existing DB (portable to Postgres, ADR-001).

## Consequences

- All new endpoints **must** land under `/api/v1` (enforced by review + a route-lint test);
  legacy unversioned routes get deprecation headers and a documented removal window.
- Auth middleware must exempt only what's intended (`/metrics` scraping by Prometheus,
  health probes) — misconfiguration would take monitoring down, so parity with
  [ADR-002](ADR-002.md)'s scrape path is part of the DoD.
- Client-side updates: MCP server, Tauri, scripts must obtain keys and resend them
  (`Authorization: Bearer …` or `X-API-Key`); dual-accept window before enforcement.
- Per-key/per-org limits need storage + counter reads on hot paths — keep it cheap (cached
  counters; DB async updates).
- Documentation obligation: an API contract doc (versioned) becomes the source of truth —
  feeds the catalog (ADR-004) and future MCP expansion.

## Rejected alternatives

- **Auth without versioning:** rejected — future breaking fixes would still fan out to all
  consumers uncontrolled.
- **Versioning without auth:** rejected — leaves the Critical gap (G2) open.
- **IdP-first (Keycloak/Ory):** DEFER — new services; external IdP arrives only at the
  first external-role/SSO requirement; Auth.js providers come before any self-hosted IdP.
- **mTLS/IP allowlists:** rejected — brittle for desktop/mobile/script clients and useless
  for scoping individual actions.
- **Status quo (open API):** rejected — violates day-1 security expectations for anything
  beyond localhost.

## Migration implications

- Phase 8: API keys + RBAC + admin v1 ship together (same permission vocabulary).
- Steps: define action/scopes list → key tables (additive DDL) → middleware (exempt list)
  → issue keys to known consumers → dual-accept → enforce → deprecate legacy routes with
  headers → removal in a future minor with changelog.
- Keys are hashed at rest (never plaintext, never committed — secrets policy); rotation
  supported by issuing a second key then revoking the first.
- Postgres cutover ([ADR-001](ADR-001.md)) carries key/limit tables unchanged; versioned
  contract docs need no migration.
