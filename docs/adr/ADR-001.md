## Context

The canonical linguistic store is `data/zolai.db` (SQLite WAL, ~2.3 GB, 105 tables live
2026-09-29, ~3.3M rows). Two facts shape the database future: (1) `zolai-web` already runs
**Prisma on PostgreSQL** (66 models), so Postgres exists in the platform's mental model;
(2) `zolai-core/zolai/data/database_layer.py` already exists as a data-access bridge alongside
`database.py`, `integrity.py`, `migrations.py`. PostgreSQL 18 shipped 2025-09-25 with
async I/O (up to 3× read improvements), `uuidv7()`, and OAuth 2.0 authentication
(verified: postgresql.org release notes, 2026-09-29).

## Problem

SQLite is single-writer: concurrent ingestion + API writes + quality runs contend on one
writer lock even with WAL. As the platform grows (quality harness writing rule results,
catalog tables, `pipeline_runs`, admin UI, dual web/CLI writers), write contention and the
lack of a managed multi-user grants model become real constraints. Doing nothing means a
later migration will be larger and riskier; migrating now without evidence means rewriting
a working system — which project constraints forbid.

## Options

1. **Adopt PostgreSQL 18 as TARGET now, keep SQLite running** — bridge via
   `database_layer.py`, dual-run, founder-gated cutover (Phase 3 → Phase 4).
2. Stay on SQLite indefinitely — accept single-writer limits, revisit on pain.
3. Adopt DuckDB as canonical — analytical speed, but not multi-writer, not a server DB.
4. Adopt ClickHouse as canonical — columnar, but overkill below ~10M rows and adds a service.
5. Migrate to some other RDBMS (MySQL/MariaDB) — no evidence of benefit; breaks the
   "Prisma already on Postgres" alignment.

## Decision

**ADOPT Postgres 18 target; KEEP SQLite now.**

The canonical target engine is PostgreSQL 18, reached through the existing
`database_layer.py` bridge with a **dual-run period** (SQLite remains authoritative until
the founder approves cutover). Net new containers in v1: 0–1 (Postgres only, Phase 3).
Tag: **CONFIGURE** bridge + **ADOPT** Postgres 18 target.

## Reasons

- **Constraint default:** "PG default canonical" is a stated project constraint; choosing
  anything else needs evidence we do not have.
- **Prisma already on PostgreSQL** in zolai-web — one relational engine across the platform
  removes a whole class of tooling/backup/auth divergence.
- **`database_layer.py` exists** — the abstraction needed for dual-run is already in tree;
  this is an extension, not a rewrite (per "do not rewrite working systems without evidence").
- **PostgreSQL 18 capability jump** (AIO, `uuidv7()` for time-ordered keys, OAuth auth)
  verified from official release notes — reduces future scaling pressure.
- **No popular-tool bias:** SQLite → Postgres is the boring, default, widely-supported path.

## Consequences

- A dual-run phase must exist: reads/writes routed through the bridge, parity checks, and
  an explicit founder-signed cutover gate (Phase 3 → Phase 4).
- Migration work (mapping, dry-run, backup→checksum→apply→verify) is scheduled in later
  batches (`docs/planning/DATA_PLATFORM_MIGRATION.md`, batch 3).
- Some SQLite-specific SQL (WAL pragmas, `INSERT OR REPLACE` idioms, `AUTOINCREMENT`
  behavior, type-affinity) will need dialect handling in the bridge layer.
- Backup discipline changes: from copying one file to `pg_dump`/WAL archiving plus the
  existing `data/` file backups.
- Postgres is the **only** new container possibly added in v1 — operational cost is bounded
  and acknowledged.
- Table-count doc drift (live 105 vs documented 101) must be re-audited during Phase 0/2.

## Rejected alternatives

- **Stay SQLite forever:** rejected — single-writer contention is a known ceiling and the
  gap register already tracks it as High severity (G1).
- **DuckDB:** rejected as canonical — not multi-writer; it remains acceptable later as an
  embedded ad-hoc analytical reader.
- **ClickHouse:** rejected — overkill below ~10M rows and adds a service against the
  zero-new-infra rule.
- **Other RDBMS:** rejected — no evidence, breaks Prisma alignment.

## Migration implications

- **Phase 0:** backup + checksum baseline of `data/zolai.db` before anything moves.
- **Phase 2:** schema mapping OLD→NEW review — **migrate, do not blind-rename** (see
  [ADR-015](ADR-015.md)).
- **Phase 3:** Postgres 18 bring-up, dual-read parity, bridge routing.
- **Phase 4:** cutover — **gated on founder sign-off (UNKNOWN: cutover timing,
  needs-founder-decision)**; rollback = keep SQLite authoritative and repoint bridge.
- Every data change follows: backup → checksum → dry-run → apply → verify.
