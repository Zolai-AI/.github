# ADR-006: No orchestrator service in v1

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-29 |
| Decision owner | founder |
| Decision | **CONFIGURE cron/systemd + pipeline_runs + CLI; DEFER orchestrator** |
| Revisit when | ≥10 interdependent pipelines or missed runs → Dagster (asset-centric) |
| Evidence | [Tool matrix §6](../research/data-platform-tool-matrix.md) · [Current-state §6](../architecture/current-state.md) |

## Context

Current batch work: JSONL ingestion (`jsonl_pipeline` v1–v3, `import_log` with 92
recorded runs), `scripts/pipelines/` (ingest_v2, clean, align, deduplicate, export,
convert_linguistics, convert_usx, collect, run), maintenance scripts, eval runs, and CI in
GitHub Actions. That's roughly **6–10 batch jobs**, mostly independent, run by one person.
There is **no `pipeline_runs` bookkeeping table** (gap G7) — runs are only partially
logged. The 2026 community consensus for 1–3 engineer teams favors no orchestrator or a
Prefect-class lightweight tool (claim: unverified — secondary source from planner research).

## Problem

Without a run ledger we cannot answer "did last night's ingest run, how long, did it fail?"
except by reading logs — and there is no central place to see it. But standing up an
orchestrator (Airflow-class = scheduler + webserver + workers + metadata DB) to answer that
for ~10 jobs is disproportionate: new service(s), new upgrade surface, new failure modes,
violating the zero-new-infra v1 rule.

## Options

1. **Configure cron/systemd timers + a `pipeline_runs` table + CLI run recording**
   (recommended).
2. Apache Airflow — full DAG orchestration.
3. Prefect — Python flows with a server.
4. Dagster — asset-centric orchestration.
5. n8n — low-code automation.
6. Queues without an orchestrator: BullMQ (Redis), Celery (broker), Temporal (durable
   workflows).
7. Do nothing (keep status quo logging only).

## Decision

**CONFIGURE cron/systemd + `pipeline_runs` + CLI; DEFER orchestrator.**
Tags: **CONFIGURE** scheduling on the existing host + **BUILD** a `pipeline_runs` ledger
wired into CLI entry points (`zolai`, `zolai-eval`, pipeline scripts); **DEFER** all
orchestrator services to the revisit trigger.

## Reasons

- **~6–10 mostly-independent jobs, solo operator** — a table + timer beats a service at
  this scale; job code already exists as CLIs.
- **Bookkeeping is the actual gap, not scheduling** — `pipeline_runs` (name, args, started,
  finished, status, rows_affected, git commit) gives auditability comparable to
  `import_log` but generalized.
- **Failure handling is trivial at this scale** — cron exit codes + the alert stack
  (ADR-002) cover "missed/failed run" alerts via one Grafana rule later.
- **Reversibility:** the pattern stays valid even after an orchestrator arrives — pipelines
  keep writing run rows; the orchestrator merely calls them.

## Consequences

- Every batch entrypoint must record a run row (**BUILD**, enforced by convention + a small
  helper in the CLI layer).
- Inter-job dependencies stay implicit (documented order in `docs/pipelines/*`) — acceptable
  while jobs are independent; growing complexity is exactly what the trigger detects.
- Missed-run detection needs a simple staleness check (e.g. "ingest has no success row in
  24h" alert rule) — added to the existing alert-parity set (ADR-002), not a new tool.
- Contributors cannot assume DAG-style retries/backfills; reruns are manual CLI invocations.

## Rejected alternatives

- **Airflow:** rejected — multi-component heavyweight for ~10 jobs.
- **n8n:** **REJECT** — Sustainable Use License restricts use to internal business purposes
  (verified: docs.n8n.io + GitHub LICENSE.md, 2026-09-29); also the wrong shape (UI flows
  ≠ batch data pipelines).
- **Prefect / Dagster now:** rejected — each is a new service; Dagster remains the
  **preferred** choice when the trigger fires.
- **Temporal:** rejected for v1 — durable long-running workflows are not our workload.
- **BullMQ / Celery:** rejected — no queue need yet; would add Redis/broker + worker.
- **Status quo without ledger:** rejected — gap G7 Medium; auditability requirement
  (reproducible transformations) unmet.

## Migration implications

- Phase 7 of the roadmap: `pipeline_runs` table (additive DDL) + CLI wiring + cron entries.
- When the Dagster trigger fires: pipelines are already CLI-invocable and stateless-ish, so
  Dagster assets wrap them with minimal change; `pipeline_runs` becomes a source of
  historical runs (import or backfill).
- No data migration risk: new table only; untouched by SQLite→Postgres mapping except for
  portable DDL ([ADR-015](ADR-015.md)).
