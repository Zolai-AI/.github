# ADR-004: Lightweight in-repo data catalog instead of enterprise catalogs

| | |
|---|---|
| Status | **ACCEPTED** |
| Date | 2026-09-29 |
| Decision owner | founder |
| Decision | **BUILD lightweight (catalog tables + generated docs + /api/v1/catalog); DEFER enterprise** |
| Revisit when | Multi-team consumers or >200 governed assets → DataHub first (clean Apache 2.0) |
| Evidence | [Tool matrix §4](../research/data-platform-tool-matrix.md) · [Current-state gap G4](../architecture/current-state.md) |

## Context

The only catalog today is prose: `docs/database/tables.md` (101 tables documented,
updated 2026-09-28 — live count 105, audit gap G14). It is maintained by hand and has
already drifted from the live DB. The wider catalog market moved in 2026: **Amundsen was
archived September 2026** (verified: repo README banner, 2026-09-29) and OpenMetadata's
ingestion framework + UI ship under the **Collate Community License 1.0 since 1.6.0**
(verified: PyPI metadata + `openmetadata-ui/LICENSE`) — a field-of-use restriction, not OSI
open source. DataHub remains Apache 2.0 end-to-end per a secondary audit
(unverified — secondary source: Hivebook 2026-09-09 citing GitHub LICENSE).

## Problem

We need discoverability (what tables/assets exist, what they mean, who owns them, where
they came from) without paying an enterprise-catalog operating cost. OpenMetadata/DataHub
class tools historically cost 4+ services (Kafka/Elasticsearch/Neo4j-class components, or
pgQueue profiles still ~5 containers) and ~10 vCPU — absurd for a solo-founder platform
with ~100–200 governed assets that already documents itself in-repo.

## Options

1. **Build a lightweight catalog:** catalog metadata tables in the canonical DB + generated
   docs (tables stay authoritative in Git) + read-only `/api/v1/catalog` endpoints.
2. Deploy OpenMetadata (ingestion + UI).
3. Deploy DataHub (e2e Apache 2.0).
4. Do nothing (keep hand-maintained `tables.md`).
5. Amundsen — no longer viable (archived).

## Decision

**BUILD lightweight (catalog tables + generated docs + `/api/v1/catalog`); DEFER enterprise.**
Tags: **BUILD** catalog tables + generator; **CONFIGURE** `/api/v1/catalog` on the existing
API; **DEFER** OpenMetadata/DataHub to the revisit trigger (DataHub preferred there because
of its clean Apache 2.0 license).

## Reasons

- **Solo founder + ~100 assets** — the discoverability job is small enough for tables plus
  generated docs; enterprise UIs are overkill (complexity column: High vs Low).
- **Docs-first culture already works** — `tables.md`, `component-status.md`, ADRs; the
  catalog extends that pattern into the DB instead of replacing it.
- **Keeps metadata separate from canonical app data** (constraint): catalog tables describe
  assets; they do not mix into linguistic content tables.
- **Serves `/api/v1` discipline** — the catalog is a natural first citizen of the versioned
  surface (ADR-014) and feeds the MCP server's context answers later (**INTEGRATE**).
- **License hygiene:** avoiding a partial-Collate-license stack and an archived project;
  if we ever outgrow this, DataHub's Apache 2.0 posture is the cleaner escalation.

## Consequences

- We own a small schema: e.g. `catalog_assets`, `catalog_fields`, `catalog_lineage`,
  `catalog_owners` (exact spec lands in batch 2 data-model doc) — plus a generator script
  that can regenerate `docs/database/tables.md` (fixing gap G14 drift automatically).
- No automatic ingestion from connectors in v1 — assets register via pipeline code
  (**CONFIGURE**: pipelines write catalog rows as they create tables).
- Lineage depth is limited to what pipelines record; column-level lineage for the whole
  corpus is out of scope until the trigger.
- Doc drift becomes a build-time failure (generated doc must match DB) rather than a
  quarterly chore.

## Rejected alternatives

- **OpenMetadata now:** rejected — multi-service cost + ingestion/UI under Collate
  Community License (field-of-use restriction); DEFER.
- **DataHub now:** rejected for v1 — Apache 2.0 is attractive, but Kafka-class operational
  weight still violates zero-new-infra; DEFER with it as first choice at trigger.
- **Amundsen:** REJECT — archived September 2026, unmaintained.
- **Status quo (hand-edited tables.md):** rejected — already drifted (101 vs 105), gap G4 High.

## Migration implications

- Phase 2 (schema mapping) determines catalog identifiers that survive the SQLite→Postgres
  move ([ADR-015](ADR-015.md): migrate-not-rename; catalog keys must be stable).
- Phase 6 of the roadmap: create catalog tables + `/api/v1/catalog` (additive DDL only,
  idempotent — mirroring how `eval_sets`/`eval_cases` were added).
- Generator backfills from `sqlite_master` + `tables.md` as seed; afterwards docs are
  generated, not hand-edited.
- If the DataHub trigger ever fires: export catalog tables → DataHub ingestion (mapping doc
  in a future ADR); no data loss because everything is rows + Git.
